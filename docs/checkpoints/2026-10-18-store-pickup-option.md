# BUDU 门店顾客自提选项

日期：2026-10-18（Asia/Shanghai）

## 已确认需求

用户只要求增加一个“支持顾客自提”选项。门店仍沿用原身份和总启停；
只做仓库时保持启用、关闭自提。销售模块、仓储、营业填报等沿用原规则。
没有新增仓库类型或第二套经营状态。

## 本次基线与变更

- OS 精确基线：`74eb7d87c0de0d5d493c66284d72267029340d05`。
- 小程序增量基于已复核源码候选 `2b2864806cbf888113861365fc04c99c7e7b227b`。

## 接口兼容

内部目录和管理返回真实 `active` 及独立 `pickupEnabled`。
公开 `/api/customer/store-directory` 仍精确返回四字段
`{key,name,district,active}`，其中公共 active 表示顾客自提可用性，
等于 `Store.active && Store.pickupEnabled`。只在公共路由做投影，保留不可用门店身份行。
不能直接给此旧公共合同增加字段：已经部署的云函数和客户端使用严格四字段校验。

OS `/capabilities` 仅列启用且支持自提的门店，保持原 key/name 对象格式。
新自提报价、无原结算的新提交和新预支付检查此设置；沿用 STORE_CLOSED
兼容码以保留旧客户端的业务拒绝与恢复分支，文案说明暂不支持顾客自提。
查询、可信支付结果确认、回调、已有同请求交易恢复和原售后流程不增加此门槛。
配送不依赖自提门店列表，即使列表为空也保留原下单、运费和支付行为。

## 发布接续边界

本次是独立代码增量，尚未生产部署、迁移或改变任何真实门店设置。
当前源码包含 89 份迁移；原 store-management 发布控制器固定旧 SHA、88 条账本和
“无迁移”合同，不能直接复用旧命令，也不能只改计数绕过校验。
正式 Mac 发布会话需要针对实际新候选及新增 SQL 做有限适配、生成新镜像，
按会话有效发布授权接续。本次没有修改控制器、发布 CI 或工作流。

加列可保留给旧代码使用，但旧 OS 代码不会执行自提关闭规则。
一旦存在 `active=true AND pickup_enabled=false`，直接回退旧 OS 可能重新开放该地点自提。
不得为满足回退检查清除 false 或删除列；须保留此规则或使用经核实的相应回退方案。

原工作树的未知改动均保留；本次 OS 工作位于独立分支 `work/store-pickup-001`。
本地提交未推送时不在远端，跨设备需使用本轮增量 bundle/patch 或后续普通推送。
